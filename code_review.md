## Замечания

### 1. Безопасность / конфигурация

- [ ] **Закоммиченный hard-coded пароль администратора.** В `src/main/resources/application.yml` и `src/test/resources/application.yml` добавлены `spring.security.user.name=admin`, `password=admin`. Это встроенный механизм Spring Boot In-Memory User: в продакшене при наличии этого свойства создаётся пользователь с известным паролем. Пароль должен уходить во внешнюю конфигурацию (переменные окружения / secrets), а не в git.
- [ ] **H2 console включена в main и test профилях** (`spring.h2.console.enabled: true`). Консоль доступна под `/h2-console` без аутентификации (в `SecurityConfig` — `.permitAll()` для `/h2-console/**`, CSRF там отключён). Это допустимо только для dev; в production-сборке console должна быть выключена профилем.
- [ ] **Валидация на уровне сущности (`@NotBlank` на `RatingParameters.code/description`) не покрывает метод `POST /rating_parameters/edit`.** Там `RatingParameters toSave` мапится без `@Valid`, и пустые/отсутствующие поля формы попадают в БД (метод обновляет `description/minValue/maxValue/coefficient`). Либо добавить `@Valid` на `save(...)` с обработкой ошибок, либо явно не трогать поля, которые форма не передаёт.
- [ ] **Валидация числовых полей отсутствует.** На `RatingParameters.minValue/maxValue/coefficient` нет ограничений (`@DecimalMin/@DecimalMax/@Positive`). Валидность диапазона (min ≤ max и т.п.) сейчас нигде не проверяется; в БД может попасть min > max.

### 2. Поведение API / обработка ошибок

- [ ] **Нет `@ControllerAdvice` для обработки ошибок.** `ResponseStatusException`, `MethodArgumentNotValidException`, `TypeMismatchException`, `NullPointerException` (из `edit/save`) диспетчеризуются в `/error` и логируются как ERROR через `SimpleErrorController`. Для ожидаемых бизнес-ошибок (дубликат кода, невалидный id) это даёт шумный error-лог (ERROR на каждый 400). Рекомендуется: отдельные хендлеры с нормированными статусами, или по крайней мере логирование ожидаемых ошибок на WARN.
- [ ] **`edit`/`save`: `UUID.fromString(id)` без try/catch.** Мусорный id в `/rating_parameters/edit?id=abc` → `IllegalArgumentException` → 500 (не 400). Это противоречит новому согласованному контракту: «плохой ввод = 400» (см. `RatingParametersService.deleteById`, который возвращает 400 для мусорного UUID).
- [ ] **`edit`: `orElseThrow(NullPointerException::new)`** — NPE → 500. Отсутствие записи должно быть 404 (`ResponseStatusException(HttpStatus.NOT_FOUND, ...)`), как сделано в сервисе delete.
- [ ] **Непоследовательность статусов в `delete`.** Невалидный UUID → 400 (в `RatingParametersService`), но пустой/отсутствующий id → тоже 400 через Bean Validation (`@NotBlank`). Это согласовано, но стоит зафиксировать контракт: обычно «невалидный формат» = 400, а «пустое значение обязательного параметра» — тоже 400 допустимо. Однако в `create` пустой code → 400 (Bean Validation), а дубликат кода → тоже 400 (`ResponseStatusException`). Рекомендуется: дубликат уникального поля = 409 Conflict, а не 400 — это стандартный REST-контракт.
- [ ] **`SimpleErrorController`: отсутствие атрибута `ERROR_STATUS_CODE`.** При редиректе на `/error` без атрибута статусов (например, при прямой навигации) контроллер вернёт шаблон `"error"`, но ответ будет 200 OK. Стоит вернуть корректный статус через `ResponseEntity` или использовать стандартный `BasicErrorController`.
- [ ] **403 от `@PreAuthorize` не обрабатывается.** При успешной аутентификации без роли ADMIN Spring Security вернёт 403 (AccessDeniedException). В `SimpleErrorController` есть ветка на `FORBIDDEN` → `403page`, но нужно убедиться, что 403 действительно диспетчеризуется в `/error` (в текущей конфигурации ExceptionTranslationFilter при аутентифицированном пользователе с insufficient rights вызывает AccessDeniedHandler по умолчанию, который отвечает 403 напрямую без forward на /error). Тесты проверяют только `status().isForbidden()`, но не факт, что отдаётся HTML-страница.

### 3. Дизайн / архитектура

- [ ] **Дублирование бизнес-логики: `create` vs `delete`.** Уникальность кода и save в контроллере (`create`), а UUID-парсинг/удаление — в сервисе (`RatingParametersService`). Рекомендую вынести всю логику CRUD в один сервис (например, `RatingParametersService.create`, `.delete`, `.getPaged`) для единообразия и тестируемости.
- [ ] **`@PreAuthorize("hasRole('ADMIN')")` дублируется.** У класса контроллера уже стоит метод-безопасность на уровне класса; в оригинале она дублировалась на каждом методе (убрано — хорошо). Но `SimpleErrorController` и другие публичные эндпоинты должны явно покрываться разрешением `/error` (сейчас есть).
- [ ] **Несогласованность сигнатур DTO.** `RatingParametersPageRequest` использует `int page = 1`, а `RatingParametersDeleteRequest` — `String id`. Это допустимо (page/size — числа), но стоит согласовать: если в будущем появится `@Pattern(UUID)` на delete, то DTO-подход уже заложен.
- [ ] **Пагинация без сортировки по умолчанию.** В `getAll` добавлена `Sort.by("code")`, что хорошо. Но нет защиты от огромного `size`: `?page=1&size=999999` → выборка всей таблицы. Рекомендую верхний предел на size (например, через DTO-валидацию `@Max(100)`).
- [ ] **`RatingParametersService.deleteById(String id)` принимает String** — это следствие маппинга query-параметра в DTO. Если в будущем потребуется вызывать из других мест (REST API), лучше иметь overload с UUID. Мелочь, но стоит учесть.

### 4. Тесты

- [ ] **`ContextTest.test()` пустой.** Метод без тела — это не тест, а «заглушка». Либо удалите его, либо дайте осмысленное тело (например, проверка загрузки контекста).
- [ ] **Тесты delete не проверяют HTML-страницу 400/404.** `DeleteTest` проверяет только статус кода (`isBadRequest()`, `isNotFound()`), но не факт, что отдаётся именно `400page.html` / `404page.html`. В `CreateTest` есть тест на HTML-страницу для 400 (`errorPageFor400ReturnsHtmlWithoutAuthentication`), аналогичного нет в DeleteTest.
- [ ] **Тесты не покрывают сценарии `edit`/`save`.** После рефакторинга create/delete/getAll покрыты, но методы `edit` (GET/POST) остаются без тестов, хотя их поведение (500 на мусорный id, NPE при отсутствии записи) важно зафиксировать.
- [ ] **Параллельность тестов и общий H2 file DB.** Тесты используют `jdbc:h2:file:./test/demo` с `generate-ddl: false`. Если CI/CD или несколько разработчиков будут параллельно гонять `mvn test`, возможна конкуренция за файл БД. Рекомендую mem-базу для тестов (`jdbc:h2:mem:testdb;DB_CLOSE_DELAY=-1`) как было ранее, или `@DirtiesContext`/изолированные имена БД на процесс.
- [ ] **Удаление `test.sql`.** Ранее тесты инициализировались через `data-locations: classpath*:test.sql`; теперь `spring.sql.init.mode=always` без `data-locations`, а данные — из уже существующего файла `./test/demo.mv.db`. Это создаёт скрытую зависимость от состояния БД на файловой системе (см. п. «Параллельность тестов»). Если файл отсутствует, тесты упадут при старте (generate-ddl: false).

### 5. Сборка / инфраструктура

- [ ] **JDK 25 как JRE без javac.** В `pom.xml` закомментировано: «JDK 25 доступен только как JRE (javac отсутствует), поэтому сборка идёт через ECJ». Это необычная конфигурация — обычно в CI/локальной среде есть полноценный JDK. Стоит задокументировать, почему именно ECJ, и проверить, что Lombok-аннотации корректно обрабатываются (сейчас тесты зелёные, но при изменении версий может сломаться).
- [ ] **Апгрейд Spring Boot 3.3.5 → 3.5.0 + Java 17 → 25.** Крупный скачок. Рекомендую убедиться, что все зависимости (thymeleaf-extras-springsecurity6 и др.) совместимы с новым Spring Security 6.5+; проверены ли breaking changes?
- [ ] **`mvnw` получил execute permission** (`old mode 100644 → new mode 100755`). Это нормально, но стоит зафиксировать в `.gitattributes`/CI, чтобы не ломалось на Windows.

### 6. Качество кода / стилистика

- [ ] **Комментарий «JDK 25 доступен только как JRE»** в `pom.xml` — это комментарий для конкретного окружения автора; в общем проекте он будет misleading. Стоит убрать или переформулировать.
- [ ] **Опечатка в сообщении commit'а**: «рефакториг» вместо «рефакторинг». Мелочь, но стоит поправить в следующем коммите (или не фиксировать историю).
- [ ] **Импорт `org.springframework.web.server.ResponseStatusException`** — это из `spring-web`, а не из webmvc. Использование в MVC-контроллере корректно (Spring Boot мапит его), но стоит убедиться, что при переходе на Spring WebFlux или другом стеке это не сломается.
- [ ] **Импорт `List`** в контроллере остался после удаления использования (`import java.util.List;`) — неиспользуемый импорт. Проверить IDE-предупреждения.

### 7. Шаблоны / UI

- [ ] **Форма удаления внутри таблицы.** `<form th:action="@{/rating_parameters/delete}" th:method="post">` в ячейке строки — это стандартный приём, но при большом числе строк каждая строка содержит отдельную форму (немного «тяжёлый» HTML). Альтернатива: одна форма на всю таблицу с `name="id"` динамически. Мелочь.
- [ ] **`confirm()` без локализованной строки.** Текст подтверждения хардкодирован в шаблоне; при локализации потребуется вынос в messages.properties.
- [ ] **Bootstrap 4 + CDN.** Старая версия (4.0.0), при апгрейде до Bootstrap 5 API форм/кнопок меняется. Если есть планы миграции — стоит учесть заранее.

## Резюме

Качество рефакторинга высокое: пагинация вынесена в БД, Bean Validation защищает входные параметры, тесты покрывают ключевые сценарии (35/35 зелёные). Основные риски:
1. **Безопасность**: hard-coded пароль и включённая H2 console в main-профиле — нужно вынести во внешнюю конфигурацию.
2. **Непоследовательность обработки ошибок**: `edit`/`save` возвращают 500 на мусорный id, тогда как delete/create — 400; нет `@ControllerAdvice`; дубликат кода = 400 вместо 409.
3. **Тесты**: пустой `ContextTest`, отсутствие HTML-проверок в DeleteTest, зависимость от файловой БД (риск параллельности).
